Session

Second factor required

The login returned a challenge. Its token is held in a separate short-lived cookie — a session cookie will not open these routes. 


      


      

        
Passwordless login

        

          No password: a one-time code is emailed or texted to an existing
          user, then verified here to start a session. A tenant with MFA
          enabled still enforces its second factor afterward, same as the
          Session card.

Delete account

Custom objects

        

          Needs a custom-object schema configured in the tenant and named in
          LR_CUSTOM_OBJECT_NAME. Without it these routes report
          which variable is missing rather than failing upstream.
        

        
        
        

          
        

        
        
        

          
          
        

        

      


      

        
Access token

        

          Refresh uses the /manage/ operation. The native variant takes
          the access token as a query parameter, which would put a bearer credential
          into access and proxy logs. Refreshing rotates the session's tokens
          server-side, so the cookie does not change.
        

        

          
          
          
        

        

      


      

        
Multi-factor authentication

        
        

          Optional. Where Duo returns the user after its challenge — only needed if
          this tenant has Duo configured. Left blank, the parameter is omitted
          entirely rather than sent empty.
        

        

          
          
        

        
        
        

      


      

        
Passkey

        

          WebAuthn needs a secure context. http://localhost counts, so
          this works as shipped; over plain HTTP on any other host the browser refuses.
